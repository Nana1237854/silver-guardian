# 银发守护者 APP 照护闭环功能扩展需求文档

## 1. 文档概述

### 1.1 项目背景

“银发守护者 APP”是一款面向老年人的移动端照护应用，当前已经具备健康档案、用药提醒、家人相册、家属联系人、防诈骗提醒、便民查询、天气出行建议、智能对话等基础功能。

随着功能逐步完善，项目需要从“功能集合”进一步升级为“日常照护闭环系统”。本次需求围绕老年人日常安全、用药反馈、家属远程照护、紧急求助和适老化学习成本等问题，提出 6 个功能扩展方向。

### 1.2 本次新增需求范围

| 编号 | 功能名称 | 核心目标 |
|---|---|---|
| 1 | 每日平安确认 | 让老人每天主动确认状态 |
| 2 | 异常未响应提醒 | 发现老人长时间未响应的潜在风险 |
| 3 | 服药后身体反馈 | 记录服药后的不适反应 |
| 4 | 家属端照护摘要 | 汇总老人每日健康、用药、相册和告警状态 |
| 5 | 一键求助增强 | 自动整合求助信息，提升紧急求助效率 |
| 6 | 适老化操作引导 | 降低老人首次使用 App 的学习成本 |

---

## 2. 需求目标

### 2.1 产品目标

1. 将 App 从“单个功能模块集合”升级为“老人日常照护闭环系统”。
2. 提高老人主动报平安、用药反馈、紧急求助的便利性。
3. 帮助家属更高效地了解老人当天状态。
4. 通过适老化操作引导降低老人使用智能手机的难度。
5. 在课程项目答辩中体现系统的完整性、实用性和人群针对性。

### 2.2 用户目标

#### 老人用户

1. 每天可以用最简单的方式确认自己状态。
2. 身体不舒服时能快速联系家属。
3. 服药后可以记录不良反应。
4. 遇到紧急情况时不用组织复杂语言，系统自动生成求助信息。
5. 第一次使用功能时能看懂按钮含义和操作步骤。

#### 家属用户

1. 可以快速了解老人当天是否平安。
2. 可以看到老人服药完成情况。
3. 可以查看老人最近健康状态和异常提醒。
4. 老人未响应或求助时能获得更完整的信息。
5. 减少反复询问老人“吃药了吗”“今天怎么样”的沟通成本。

## 3. 功能一：每日平安确认

### 3.1 需求背景

独居或半独居老人可能不会每天主动联系家属。若老人身体不适、摔倒或手机操作困难，家属往往无法及时知道。因此需要一个简单、固定、低打扰的“每日平安确认”机制。

### 3.2 功能描述

系统每天在固定时间向老人展示“今日平安确认”卡片，老人只需点击一个按钮即可完成当天状态反馈。

推荐入口：

1. 首页顶部卡片；
2. 通知提醒；
3. 设置页中的“每日平安确认”开关；
4. 家属端照护摘要中展示确认结果。

### 3.3 页面设计

卡片标题：

```text
今日平安确认
```

卡片描述：

```text
今天感觉还好吗？点一下，让家人放心。
```

状态按钮：

```text
我很好
身体不舒服
需要联系家人
稍后提醒我
```

### 3.4 业务流程

```text
每天到达设定时间
↓
首页显示“今日平安确认”卡片
↓
老人点击状态按钮
↓
系统保存今日确认记录
↓
首页显示“今日已确认”
↓
家属端照护摘要同步显示今日状态
```

### 3.5 数据字段建议

新增模型：

```java
SafeCheckRecord
```

字段建议：

```text
id
userId
status
note
checkedAt
date
```

status 可选值：

```text
OK：我很好
UNWELL：身体不舒服
NEED_FAMILY：需要联系家人
REMIND_LATER：稍后提醒
MISSED：未响应
```

### 3.6 功能规则

1. 每个用户每天只保留一条主要平安确认记录。
2. 老人可在当天重复修改状态，以最后一次为准。
3. 点击“我很好”后，首页卡片变为“今日已确认”。
4. 点击“身体不舒服”后，系统建议记录健康数据或联系家属。
5. 点击“需要联系家人”后，跳转到家属联系人或一键呼叫。
6. 点击“稍后提醒我”后，可延迟 30 分钟或 1 小时再次提醒。
7. 如果当天未确认，则进入“异常未响应提醒”逻辑。

### 3.7 验收标准

1. 首页可以显示每日平安确认卡片。
2. 点击不同状态后，系统可以保存记录。
3. 当天再次进入首页时，可以看到确认状态。
4. 家属端照护摘要可以读取当天确认结果。
5. 切换用户后，不同用户的平安确认记录互不影响。

## 4. 功能二：异常未响应提醒

### 4.1 需求背景

老人发生异常时，可能无法主动点击 SOS，也可能没有能力打电话。因此，仅依赖主动求助是不够的。系统需要关注老人“长时间没有回应”的情况。

### 4.2 功能描述

如果老人到了设定时间仍未完成每日平安确认，系统会进行分级提醒：

| 阶段 | 条件 | 系统行为 |
|---|---|---|
| 第一次提醒 | 到达确认时间未确认 | 发送本地通知 |
| 第二次提醒 | 超过 3 小时未确认 | 首页显示明显提醒 |
| 异常记录 | 超过 6 小时未确认 | 生成未响应告警 |
| 家属提示 | 存在家属联系人 | 提示联系家属或模拟通知家属 |

### 4.3 业务流程

```text
到达每日确认时间
↓
检查今日是否已有 SafeCheckRecord
↓
如果没有确认
↓
发送本地提醒
↓
继续等待
↓
超过阈值仍未确认
↓
写入 EmergencyAlert
↓
家属端照护摘要显示“今日未响应”
```

### 4.4 提醒文案

第一次提醒：

```text
今日平安确认
点一下“我很好”，让家人放心。
```

第二次提醒：

```text
还没有完成今日平安确认
如果身体不舒服，可以一键联系家人。
```

异常告警记录：

```text
今日平安确认长时间未响应，建议家属主动联系老人确认情况。
```

### 4.5 功能规则

1. 未响应提醒不应频繁打扰老人。
2. 提醒文案避免恐吓，用温和语气表达。
3. 如果老人当天已经确认，则不再触发未响应提醒。
4. 如果老人点击“稍后提醒我”，未响应时间从延迟后重新计算。
5. 未响应记录应出现在家属端照护摘要中。
6. 可以先用本地模拟通知，不强制实现真实短信或远程推送。

### 4.6 验收标准

1. 到达设定时间未确认时，系统可以显示提醒。
2. 超过设定阈值后，系统可以生成未响应告警。
3. 完成平安确认后，不再继续提醒。
4. 家属端照护摘要可以显示“今日已确认 / 今日未响应”。
5. 不同用户的未响应逻辑互不影响。

## 5. 功能三：服药后身体反馈

### 5.1 需求背景

现有用药提醒主要关注“是否按时服药”，但对老人来说，服药后的身体反应同样重要。部分老人可能在服药后出现头晕、恶心、心慌等不适，但难以准确记录和反馈给家属或医生。

### 5.2 功能描述

老人完成服药打卡后，系统弹出一个简单反馈卡片，让老人选择服药后的身体感受。

### 5.3 页面设计

打卡后弹窗标题：

```text
服药后感觉怎么样？
```

选项：

```text
感觉正常
有点头晕
有点恶心
心慌不舒服
其他不适
暂不填写
```

如果选择“其他不适”，可以显示简单输入框：

```text
请简单描述哪里不舒服
```

### 5.4 业务流程

```text
老人点击“已服药”
↓
系统保存服药打卡记录
↓
弹出服药后反馈弹窗
↓
老人选择身体反应
↓
系统保存反馈记录
↓
如为明显不适，写入健康档案或照护摘要
```

### 5.5 数据字段建议

新增模型：

```java
MedicineFeedback
```

字段建议：

```text
id
userId
medicineId
medicineName
feedbackType
feedbackText
createdAt
date
```

feedbackType 可选值：

```text
NORMAL
DIZZY
NAUSEA
PALPITATION
OTHER
SKIPPED
```

### 5.6 功能规则

1. 只有点击“已服药”后才弹出反馈。
2. 老人可以选择“暂不填写”，避免增加操作负担。
3. 如果反馈为“头晕 / 恶心 / 心慌 / 其他不适”，应进入家属端照护摘要。
4. 同一种药如果多次出现不适，可以在后续版本中生成风险提示。
5. 反馈记录不直接给出医疗诊断，只提示“建议联系医生或家属”。

### 5.7 验收标准

1. 点击用药打卡后，可以弹出身体反馈弹窗。
2. 选择反馈后，系统可以保存记录。
3. 反馈记录可以在照护摘要中展示。
4. 选择“暂不填写”不会阻止打卡完成。
5. 不影响原有用药提醒和打卡逻辑。

## 6. 功能四：家属端照护摘要

### 6.1 需求背景

家属往往关心老人当天是否平安、是否按时吃药、健康指标是否异常、有没有告警和求助。如果这些信息分散在多个模块中，家属需要逐个查看，效率较低。

### 6.2 功能描述

系统整合多个模块数据，生成“今日照护摘要”，让家属可以快速了解老人当天整体状态。

### 6.3 数据来源

| 数据来源 | 摘要内容 |
|---|---|
| 平安确认 | 今日是否已确认，状态是什么 |
| 用药提醒 | 今日应服药数量，已完成数量 |
| 服药反馈 | 是否有服药后不适 |
| 健康档案 | 今日最新健康指标是否异常 |
| 紧急告警 | 今日是否有 SOS 或异常告警 |
| 家人相册 | 今日是否上传新照片 |
| 防诈训练 | 今日是否完成防诈学习或测验 |

### 6.4 页面设计

页面标题：

```text
今日照护摘要
```

摘要卡片示例：

```text
今日状态：已确认平安
用药情况：已完成 2/3 次
健康状态：血压正常，心率正常
服药反馈：无不适反馈
异常提醒：暂无异常告警
家庭互动：今日新增 1 张照片
防诈学习：已完成 1 次情景训练
```

### 6.5 业务流程

```text
家属进入照护摘要页面
↓
系统读取当天数据
↓
聚合健康、用药、平安确认、告警、相册等信息
↓
生成摘要卡片
↓
如存在异常，置顶显示重点提醒
```

### 6.6 功能规则

1. 摘要以“今天”为主要时间范围。
2. 如果没有数据，应显示友好提示，而不是空白。
3. 如果存在异常告警，应优先展示。
4. 摘要不需要复杂图表，重点是快速读懂。
5. 初期可做本地页面，不强制实现远程家属端同步。
6. 可以放在“家属联系人管理”或“设置页家人与设备”区域入口中。

### 6.7 数据聚合建议

新增模块：

```java
CareSummaryModule
```

或在现有 Repository / Module 中新增聚合方法：

```java
CareSummary getTodayCareSummary()
```

CareSummary 字段建议：

```text
safeCheckStatus
medicineTotal
medicineTaken
abnormalHealthCount
medicineFeedbackWarningCount
emergencyAlertCount
newPhotoCount
fraudTrainingDone
summaryText
```

### 6.8 验收标准

1. 可以进入“今日照护摘要”页面。
2. 页面能展示平安确认结果。
3. 页面能展示今日用药完成情况。
4. 页面能展示健康异常数量或状态。
5. 页面能展示服药后不适反馈。
6. 页面能展示紧急告警数量。
7. 没有数据时显示友好空状态。
8. 不影响原有健康、用药、相册、防诈模块。

## 7. 功能五：一键求助增强

### 7.1 需求背景

老人遇到紧急情况时，可能难以完整表达自己的位置、身体状态、服药情况和联系人信息。现有 SOS 如果只是拨号，信息量有限。

### 7.2 功能描述

当老人点击 SOS 或“一键求助”时，系统自动生成一段结构化求助信息，包含老人姓名、当前位置、最新健康状态、最近服药情况、紧急联系人等内容。

### 7.3 求助信息示例

```text
【银发守护者求助信息】

老人姓名：张爷爷
当前位置：广州市越秀区附近
当前健康状态：
- 血压：160/100，需关注
- 心率：110，需关注

最近用药：
- 降压药 08:00 已服用
- 降糖药 12:00 未服用

紧急联系人：
- 儿子 大明 13800001111

老人可能需要帮助，请尽快联系确认。
```

### 7.4 功能入口

1. 首页 SOS 紧急呼叫；
2. 一键呼叫；
3. 平安确认中选择“需要联系家人”；
4. 健康异常告警详情页；
5. 未响应提醒详情页。

### 7.5 业务流程

```text
老人点击 SOS
↓
系统读取当前用户信息
↓
读取家属联系人
↓
读取最新健康数据
↓
读取今日用药状态
↓
读取定位或已保存位置
↓
生成求助信息
↓
展示确认弹窗
↓
老人选择拨打电话 / 复制信息 / 模拟发送给家属
```

### 7.6 功能规则

1. 如果没有定位权限，则显示“当前位置暂不可用”。
2. 如果没有健康数据，则显示“暂无最新健康数据”。
3. 如果没有家属联系人，则提示先添加家属联系人。
4. 不强制真实短信发送，课程项目中可用“复制求助信息”或“模拟发送”。
5. 求助信息必须简洁、清楚，避免老人理解困难。
6. 如存在多个家属联系人，优先使用主要联系人或第一个联系人。

### 7.7 数据来源

| 信息 | 来源 |
|---|---|
| 老人姓名 | UserSessionModule / UserStore |
| 家属电话 | FamilyMember / UserSessionModule |
| 健康状态 | HealthRecordModule |
| 用药状态 | MedicineReminderModule |
| 位置 | WeatherModule / Location 模块 / 已保存定位 |
| 告警记录 | EmergencyModule |

### 7.8 验收标准

1. 点击 SOS 后可以生成求助信息。
2. 求助信息包含老人姓名、健康状态、用药状态和联系人。
3. 没有某项数据时有兜底文案。
4. 可以复制求助信息。
5. 可以跳转拨打家属电话。
6. 不影响原有 SOS 功能。
7. 生成过程不崩溃，不因某个模块为空而失败。

## 8. 功能六：适老化操作引导

### 8.1 需求背景

老年人使用智能手机时，常见问题不是“功能不存在”，而是“不知道点哪里”“不知道这个按钮是什么意思”“害怕点错”。因此，适老化设计不应只停留在大字体和高对比度，还应包含操作引导。

### 8.2 功能描述

为关键功能提供首次使用引导和按钮解释，帮助老人理解操作流程。

### 8.3 引导范围

| 模块 | 引导内容 |
|---|---|
| 首页 | SOS、一键呼叫、健康档案、用药提醒入口 |
| 用药提醒 | 添加药品、设置时间、已服药打卡 |
| 家属联系人 | 添加家属、编辑电话、删除联系人 |
| 家人相册 | 创建相册、上传照片、查看照片 |
| 防诈提醒 | 查看案例、学习防范措施、情景训练 |
| 平安确认 | 每日点击确认状态 |
| 一键求助 | 自动生成求助信息并联系家属 |

### 8.4 交互形式

#### 首次使用引导

用户第一次进入某个页面时，显示 1～3 步操作提示。

示例：

```text
第一步：点击这里添加药品
第二步：设置每天服药时间
第三步：到时间后点击“已服药”
```

#### 长按解释

老人长按按钮时，显示解释弹窗。

示例：

```text
“已服药”是什么意思？
表示您已经吃过这次药了，点击后家人也能知道您完成了服药。
```

#### 帮助入口

页面右上角提供“？”按钮，点击后重新播放引导。

### 8.5 功能规则

1. 引导文字必须简短。
2. 每一步只解释一个操作。
3. 引导可以关闭。
4. 用户关闭后不应每次重复弹出。
5. 设置页中可以提供“重新查看操作引导”。
6. 引导层不应遮挡返回按钮和紧急求助按钮。
7. 所有提示语避免技术词，例如“同步”“数据库”“权限”等。

### 8.6 数据字段建议

使用 SharedPreferences 保存引导状态：

```text
guide_home_shown
guide_medicine_shown
guide_family_manage_shown
guide_album_shown
guide_fraud_shown
guide_safe_check_shown
guide_sos_shown
```

### 8.7 验收标准

1. 首次进入关键页面时可以显示操作引导。
2. 用户关闭引导后，下次不重复显示。
3. 点击“？”可以重新查看引导。
4. 长按关键按钮可以显示解释。
5. 引导文字适合老人阅读。
6. 不影响原页面功能和点击操作。

## 11. 答辩说明建议

可以在答辩中这样介绍本次功能扩展：

```text
本项目后续扩展方向不是简单增加页面数量，而是围绕老年人的日常安全和家属远程照护构建闭环。

每日平安确认解决老人每天是否安全的问题；异常未响应提醒关注老人无法主动求助的情况；服药后身体反馈让用药提醒从“是否吃药”升级为“吃药后是否不适”；家属端照护摘要把健康、用药、相册、告警等信息统一汇总，方便家属快速了解老人状态；一键求助增强则在紧急情况下自动整合老人姓名、健康数据、用药状态、位置和联系人，降低老人表达困难带来的风险；适老化操作引导进一步降低老人首次使用 App 的学习成本。

这些功能共同形成“老人确认状态 — 系统记录数据 — 家属查看摘要 — 异常及时求助”的完整照护闭环。
```

## 12. 总结

本需求文档提出的 6 个功能，核心目标是让“银发守护者 APP”从基础功能型应用升级为日常照护型应用。

最终形成的产品闭环为：

```text
老人每日平安确认
↓
系统记录健康、用药、反馈和相册互动
↓
家属查看照护摘要
↓
异常未响应或健康异常时生成提醒
↓
紧急情况下通过一键求助快速联系家属
↓
通过适老化操作引导降低长期使用门槛
```

这套扩展功能既能体现对老年人真实需求的理解，也能在课程答辩中展示项目的人群针对性、业务完整性和工程扩展能力。
