## 提问 1：用药提醒完整链路（AlarmManager → BroadcastReceiver → Notification → TTS → BootReceiver）

### 导师提问

你负责的用药提醒功能涉及 AlarmManager、BroadcastReceiver、Notification 和 TTS 多个组件协作。请你说明：**从用户设置一个"每天早上 8 点吃降压药"的提醒，到手机准时响起通知和语音播报，整个链路中 AlarmManager 如何设置、BroadcastReceiver 如何接收、通知和 TTS 如何触发？如果手机重启了，提醒还能恢复吗？**

### 建议展示的关键代码

| 文件 | 定位 | 作用 |
|------|------|------|
| `MedicineAlarmScheduler.java` | `schedule()` 方法 | 解析药品 time 字段，计算触发时刻，注册 AlarmManager 闹钟 |
| `ReminderBroadcastReceiver.java` | `onReceive()` 方法 | 接收闹钟广播，判断打卡状态，创建通知并触发 TTS |
| `TtsHelper.java` | `speak()` 方法 | TTS 语音播报用药提醒 |
| `BootReceiver.java` | `onReceive()` 方法 | 监听 BOOT_COMPLETED，开机后重新注册所有用药闹钟 |
| `AndroidManifest.xml` | BootReceiver 注册 + BOOT_COMPLETED 权限 | 静态注册广播接收器 |

### 可能被追问

- AlarmManager 的 RTC_WAKEUP 和 RTC 有什么区别？为什么选 RTC_WAKEUP？
- PendingIntent 的 requestCode 是怎么生成的？多药品会不会互相覆盖？
- 如果用户在 7:59 关机，8:00 闹钟没响，8:01 开机后 BootReceiver 重新注册了 8:00 的闹钟——这个闹钟会立即触发还是等到第二天？

### 参考答辩说法

> 老师，用药提醒涉及五个组件的协作。我按时间顺序说：第一，用户在 MedicineFragment 设置药品和服用时间后，数据存入 SQLite，然后调用 MedicineAlarmScheduler.schedule()。第二，调度器解析药品的 time 字段，用 Calendar 计算下一次触发时刻，通过 AlarmManager.RTC_WAKEUP 注册闹钟——这里做了 Android 12+ 兼容，有精确权限时用 setExactAndAllowWhileIdle，否则降级为 setAndAllowWhileIdle。第三，闹钟触发时系统发送 PendingIntent 到 ReminderBroadcastReceiver。第四，Receiver 收到广播后通过 Repository 判断今天是否已打卡，未打卡则创建通知并调用 TtsHelper.speak() 语音播报。第五，手机重启后 BootReceiver 监听 BOOT_COMPLETED，重新读取所有药品数据并逐个重新注册闹钟。
>
> 答辩时我会先展示 MedicineAlarmScheduler.java 的 schedule() 方法（闹钟注册逻辑），再展示 ReminderBroadcastReceiver.java 的 onReceive()（通知与 TTS 触发），最后展示 BootReceiver.java 的开机恢复逻辑，以及 AndroidManifest.xml 中 BOOT_COMPLETED 权限和 Receiver 注册。

### 加分表达

> 主动区分 `setExactAndAllowWhileIdle()` 和 `setAndAllowWhileIdle()` 的使用条件，说明考虑了 Android 12+ 的精确闹钟权限——这体现了版本兼容意识，是加分项。

### 扣分风险

**低。** 链路上每个环节都说清楚了。如果被追问 PendingIntent 的 requestCode 是否可能冲突导致闹钟覆盖，需要能说出 currentTimeMillis 或 medicine_id 作为 requestCode 的方案。

## 提问 5：蓝牙健康设备同步（BLE）

### 导师提问

你负责了蓝牙（BLE）健康设备的数据同步功能。请说明：**BluetoothActivity 的 BLE 扫描流程是怎样的？扫描到设备后如何连接？连接成功后健康数据是怎么从设备读取并写入本地 SQLite 的？Android 12+ 的 BLUETOOTH_SCAN 和 BLUETOOTH_CONNECT 权限你是怎么处理的？如果蓝牙没开或扫描超时怎么办？**

### 建议展示的关键代码

| 文件 | 定位 | 作用 |
|------|------|------|
| `BluetoothActivity.java` | `initBluetooth()` + `startScan()` + `connectDevice()` | BLE 初始化、权限检查、扫描、连接全流程 |
| `AndroidManifest.xml` | BLUETOOTH_SCAN / BLUETOOTH_CONNECT / BLUETOOTH / BLUETOOTH_ADMIN / bluetooth_le feature | 蓝牙权限声明 |
| `BluetoothDeviceMock.java` | 设备数据模型 | 模拟设备名、类型、检测值 |
| `HealthRecordModule.java` / `Repository.java` | `addHealthData()` 方法 | 蓝牙同步数据写入 SQLite |

### 回答要点

- 初始化：判断 BLE 支持 → BluetoothManager → BluetoothAdapter → 蓝牙未开则 ACTION_REQUEST_ENABLE 引导
- 权限：Android 12+ 检查 BLUETOOTH_SCAN + BLUETOOTH_CONNECT；旧版检查 ACCESS_FINE_LOCATION
- 扫描：startScan() → 5 秒超时 → 设备名关键词过滤（BP、OX、HR、Band、Watch、"血压、血氧、心率"）→ detectType()/detectValue()

- 模拟连接：connectDevice() → healthRecords().addHealthData(type, value, "正常") → 写入 health_data 表
- 兜底：蓝牙未开/拒绝 → loadMockDevices()；不支持 BLE/扫描器不可用 → loadMockDevices()；扫描超时/无设备 → loadMockDevices()

### 可能被追问

- 如果要真正实现 GATT 连接，需要重写哪些部分？需要增加哪些类？
- 扫描到的真实设备名称一定能通过你的关键词匹配吗？如果设备名是乱码怎么办？
- Android 12+ 的 BLUETOOTH_SCAN 和 BLUETOOTH_CONNECT 权限为什么需要同时申请？

### 参考答辩说法

> 老师，蓝牙模块的完整流程是：初始化阶段检查 BLE 支持，通过 BluetoothManager 获取 Adapter，蓝牙没开就引导用户开启。Android 12+ 同时申请 BLUETOOTH_SCAN 和 BLUETOOTH_CONNECT 权限，旧版申请 ACCESS_FINE_LOCATION。扫描时调用 leScanner.startScan()，5 秒超时，设备名通过 BP、OX、HR、Band、Watch 等关键词过滤健康设备，然后 detectType() 判断血压/血氧/心率，detectValue() 生成演示值。

> 兜底很完善：蓝牙未开/拒绝、不支持 BLE、扫描器不可用、扫描超时、无设备发现等情况都走 loadMockDevices()，确保课程演示时能完成"选择设备 → 同步数据 → 写入记录"的闭环。

## 提问 7：今日照护摘要

### 导师提问

你负责了今日照护摘要（CareSummary）功能。请说明：**照护摘要页汇总了哪些信息？数据分别从哪些表或模块聚合而来？这个页面是给老人看还是给家属看的？它是实时计算还是定时生成的？设计上为什么要单独做一个摘要页而不是在各个模块里分别查看？**

### 建议展示的关键代码

| 文件 | 定位 | 作用 |
|------|------|------|
| `CareSummaryActivity.java` | 页面展示逻辑 | 照护摘要页面（家属端） |
| `CareSummaryModule.java` | 数据聚合方法 | 从各 DAO/Repository 临时读取当天数据并聚合 |
| `CareSummary.java` | 字段定义 | 摘要数据模型 |

### 回答要点

- 五类汇总信息：
  1. 今日健康指标（心率、血压、血氧、睡眠等）→ 来源 health_data 表
  2. 今日用药情况（应服几种、已打卡几种）→ 来源 user_medicines + medicine_taken
  3. 健康异常/紧急告警 → 来源 emergency_alerts
  4. 每日平安确认 → 来源 safe_check_records
  5. 家属关注信息（未响应、未服药、异常记录）
- 给家属看而非老人自己操作——老人端关注"我要做什么"，家属端关注"今天是否有异常"
- 实时计算型：打开 CareSummaryActivity 时 CareSummaryModule 从各 DAO 临时聚合当天数据
- 设计理由：降低家属查看成本——"照护驾驶舱"把分散数据集中成一句话结论和几张状态卡片

### 可能被追问

- 如果当天有 20 条健康数据，摘要里展示最新一条还是全部汇总成一个范围？
- 摘要页的刷新是自动的还是手动下拉的？用户离开再回来数据会更新吗？
- 为什么不提前定时生成（比如每天早上 8 点跑一次）而要实时计算？

### 参考答辩说法

> 老师，照护摘要页汇总五类信息：今日健康指标来自 health_data 表，用药打卡情况来自 user_medicines 和 medicine_taken 表，健康异常告警来自 emergency_alerts 表，平安确认来自 safe_check_records 表，以及家属关注的未响应、未服药等综合状态。
>
> 这个页面是给家属看的，定位是"照护驾驶舱"。老人端关注的是"我要做什么"——吃什么药、打不打卡、健康数据怎样；家属端关注的是"今天有没有异常"——有没有按时吃药、有没有确认平安、有没有异常指标。如果分别进健康、用药、平安确认多个模块查看，操作成本太高。摘要页把分散数据集中成一句"今日一切正常"或"心率偏高需关注"，让家属 3 秒就能判断是否需要联系老人。
>
> 采用实时计算而非定时生成，因为家属随时可能打开查看，而且老人可能刚刚打卡完成——实时聚合能保证看到最新状态。
>
> 答辩时我会定位到 CareSummaryModule 的数据聚合方法，展示它从多个 DAO 读取当天数据并组装成 CareSummary 对象，再展示 CareSummaryActivity 的展示逻辑。

### 加分表达

> "照护驾驶舱"的比喻让老师立刻理解为什么需要一个独立摘要页——把抽象的设计理由变成画面感
